## Abstract（原文）

> LLM agents are shaped not only by their language models, but also by the runtime harness that mediates observation, tool use, action execution, feedback interpretation, and trajectory control. While existing agent adaptation methods mainly update model parameters, many failures in deterministic, rule-governed domains stem from mismatches at the model–environment interface. We propose **Life-Harness**, a lifecycle-aware runtime harness that improves frozen LLM agents without changing model weights or evaluation environments. Life-Harness evolves from training trajectories by converting recurring interaction failures into reusable interventions across environment contracts, procedural skills, action realization, and trajectory regulation, and remains fixed for evaluation on unseen tasks. On seven deterministic environments from τ-bench, τ²-bench, and AgentBench, Life-Harness improves **116 out of 126** model–environment settings across **18 model backbones**, with an average relative improvement of **88.5%**. Harnesses evolved only from Qwen3-4B-Instruct trajectories transfer to **17 other models**, showing that Life-Harness captures reusable environment-side structure rather than model-specific behavior. These results position runtime interface adaptation as a complementary alternative to model-centric agent training.

## 一、核心主張（一句話）

> **不改模型、改介面（runtime harness）**——在 deterministic、rule-governed 環境中，讓凍結的 LLM 透過四層 lifecycle-aware 的介面介入，獲得接近專項訓練的效益且**不損失 OOD 泛化**。

---

## 二、形式化定義

```
Episode = (task x, env E [+ user U], contract C, budget B)
Agent policy:   π_θ(·|τ_t) → a_t   (θ frozen)
Trajectory:     τ_t = (C, x, o_0, a_0, o_1, ..., a_{t-1}, o_t)

Parameter Adaptation:        θ′ ← A_param(θ, T_train)            # 模型側
Runtime Interface Adaptation: H′ ← A_harness(H, T_train), θ fixed # 介面側
```

## 三、失敗分類法（Figure 3）

| 類別 | 描述 | 例 |
|---|---|---|
| **Action Realization** | 意圖合理但表達為非可執行形式 | free-form action、缺參數 |
| **Environment Contract Mismatch** | 可執行但違反工具協議 | 錯誤呼叫順序 |
| **Trajectory Degeneration** | 個體動作有效但軌跡退化 | 重複無效命令、停滯、預算耗盡 |
| **Residual Reasoning** | 推理／計算錯誤 | 語義錯誤、算錯 |

→ 不同環境瓶頸分布不同 → 需要多點介入的 harness。

## 四、四層架構（Algorithm 1）

```
1:  C′ ← EnvContract(C);  x′ ← SkillLayer(x)
2:  s₀, o₀ ← E.Init(x′);  τ₀ ← (C′, x′, o₀)
3:  for t = 0, …, B-1:
4:      a_t ← LLM(τ_t)                                       # 模型推理
5:      z_t ← RealizeAction(a_t, τ_t, C′, s_t)                # ★ 執行前攔截
6:      (s_{t+1}, o_{t+1}) ← ExecuteOrBlock(E, s_t, z_t)
7:      τ_{t+1} ← τ_t ⊕ (z_t, o_{t+1})
8:      τ_{t+1} ← RegulateTrajectory(τ_{t+1}, C′, s_{t+1})  # ★ 執行後監測
9:      if IsEnd(s_{t+1}, o_{t+1}): break
```

### 4.1 Environment Contract Layer（互動前）
- 公式：`C′ = C ⊕ ΔC`
- 將環境約束（工具使用規則、政策約束、常見陷阱）注入 system prompt

### 4.2 Procedural Skill Layer（任務條件化）
- 從訓練軌跡蒸餾技能庫 `S`
- BM25 Top-K 檢索：`K_x = TopK_{k∈S} score(x, k)`
- 將檢索到的技能注入 system prompt

### 4.3 Action Realization Layer（執行前）
- `RealizeAction(a_t, τ_t, s_t) → EXEC(a_t) 或 Block(m_t)`
- 工具 schema / 可行動作集 / 參數約束 / 任務政策 → 確定性攔截

### 4.4 Trajectory Regulation Layer（執行後）
- `RegulateTrajectory(τ_t, a_t, o_{t+1}, b_t)`
- 偵測重複 / 停滯 / 無效重試 / 預算耗盡
- 輸出：empty / 軟恢復訊息 / 重複警告 / 強糾正指令

## 九、批判性漏洞（Destroyer 視角）

1. **「Deterministic」純度被模擬用戶污染**（τ-bench 使用 LLM 模擬用戶）
2. **Codex-as-Evolver 隱性依賴**——弱 evolver 是否仍有效未知
3. **訓練 / 測試集隔離未嚴格說明**——基準任務集是否 disjoint 不透明
4. **缺乏成本／開銷分析**——API 呼叫、token 開銷、harness 規模未量化
5. **BM25 純詞袋**限制——語意泛化弱於 dense retrieval
6. **Action Realization 並非完全確定性**——對 free-form action 引入模型依賴
7. **「擊敗訓練」結論需謹慎**——可能反映 catastrophic forgetting 而非純粹介面進化優勢
